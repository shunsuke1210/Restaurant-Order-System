# Tech

## 全体方針

一人での開発・保守を前提に、**運用の手間とコストを最小化するマネージドサービス（BaaS）中心の構成**を採用する。自前でのサーバー構築・保守は行わない。

## 技術スタック

- **言語**：TypeScript（フロントエンド・バックエンドとも統一し、型を共有する）
- **フロントエンド**：Next.js
  - 客注文用（QRオーダーPWA）・厨房KDS用・レジ用の3つの画面を、別々のアプリとしてではなく**単一のNext.jsプロジェクト内のルート（役割別）として実装**する。データモデルとAPIを共有でき、一人保守での変更コストを下げるため
  - レジ画面は通常モード（店員向け：入退店管理、会計確認）と、店主が追加ログインすることで昇格する**オーナーモード**（商品登録・価格変更、売上管理）を持つ。独立した管理者用アプリは作らない
  - 客注文画面はPWA化し、ホーム画面への追加やオフライン時の簡易表示に対応できるようにする
- **バックエンド/DB**：Supabase（PostgreSQL）
  - リレーショナルなデータ（卓・セッション・注文・メニュー・売上）を扱うためPostgresを採用
  - Supabase Realtime（Postgresの変更をWebSocketで配信）を使い、注文発生を厨房KDS画面・レジ画面（卓別金額表示）へ即時反映する
  - Supabase Auth は**オーナーモード昇格のみ**に使う。客側（QRオーダー）、厨房、レジ通常モードはいずれも認証なしで利用する（厨房/レジタブレットは店舗内固定設置であること自体がアクセス境界であり、店員個人のアカウントは発行しない）
  - Row Level Security（RLS）で店舗ID単位のデータ分離、および「一般公開操作」と「オーナー専用操作（商品登録・価格変更・売上閲覧）」の権限分離を行う。将来の複数店舗展開にも備える
- **ホスティング**：
  - フロントエンド：Vercel
  - バックエンド：Supabase（マネージド）
  - いずれもアクセス量に応じたスケール・従量課金であり、小規模運用では無料枠に収まる可能性が高い

## 設計上の約束事

- **多言語非対応だが将来拡張は妨げない**：メニュー等のテキストは将来の多言語化を考慮し、単一言語のカラムに直接埋め込むのではなく、拡張しやすいスキーマ（言語コード単位のテーブル/カラム追加で対応できる形）にしておく。ただしv1では日本語のみ実装する
- **卓セッションはサーバー側の真実（source of truth）とする**：QRコード自体にセッション情報を持たせず、常にサーバーに現在有効なセッションを問い合わせる設計とする
- **決済処理そのものは持たない**：金額集計まではシステムの責務とし、現金/カード等の実際の受け渡しは対象外とする
